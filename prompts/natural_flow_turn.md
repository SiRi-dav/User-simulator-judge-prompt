# USER 自然流畅评测 Turn 级

## 任务

根据给定上下文，评价目标 USER 回复的交互推进是否合理。评价结果用于定位用户交互缺陷，支持对话使用和用户模拟器改进。

只评价输入正文的最后一条 USER 消息，其前面的消息仅作上下文。不要预设对话来源。这里的“自然流畅”是交互动作的承接与推进合理性，不是措辞、语法、礼貌、口语化、真人感、专业程度或任务完成率。不评价助手质量，也不判断案例答案是否泄漏。

综合 T1、T2、T3，给目标 USER 回复一个 1–5 的整数总分。三个角度只作诊断，不分别打分，不按问题标签个数扣分。

## 输入

输入是一段会话的文本前缀，不需要转成 JSON。可包含会话标题和元数据，正文由 `**User:**`、`**Assistant:**` 标记消息；也接受不加粗的 `User:`、`Assistant:`，忽略角色名称大小写。角色标记后的内容可在同一行或后续多行；空行、换行和缩进不代表新消息。正文中的引文、代码块或角色名称提及不应被当作新的外层消息；边界无法可靠辨认时返回 insufficient_evidence，不猜测。

- 一次只输入一个会话，按原始顺序保留从开场到目标 USER 的全部正文，并在目标 USER 处截断。最后一条消息必须为 USER；不要附带其后的助手消息或未来用户回复。若末条不是 USER 或混入多个会话，返回 insufficient_evidence，要求在 limitations 中说明需重新切分。
- 唯一评分对象是正文最后一条 USER；它直接回应的前置助手和更早消息只提供上下文。没有前置助手的开场 USER 为 not_applicable。
- 按外层消息出现顺序统一编号 m1、m2、m3……，USER 和 ASSISTANT 都计数；标题和元数据不计数。输出 target_user_id 和 evidence.message_id 均使用此编号。例如开场 USER=m1，首条 ASSISTANT=m2，首条用户回应=m3。正文不要求预先提供 id。
- 应提供完整历史前缀；若显然缺失更早内容，仅评价可见范围，并说明局限。缺少记录不代表此前没有操作。不得补造原始案例、隐藏知识、工具日志或标准操作路径。

元数据规则：
- `case_id`、`session_index` 和标题仅用于识别会话，不参与评分。
- `turn_count` 不决定消息数量、目标位置或可评分轮数；一律根据正文识别。
- `solution_status`、`stop_reason` 是整段会话的结果信息，调用方应在 turn 输入中删除，避免透露未来。若仍被附带，完全忽略，不据此判断本轮是否合理，也不引用为证据。

## 关键概念和公共规则

1. 交互动作：用户在发言中做的事，包括回答、追问、猜测、表达操作意愿、报告操作和结果、质疑、拒绝、暂停或结束；不只指操作设备。
2. 当前交互状态：截至本轮可见的信息、已报告操作及结果、未解决问题、待回应请求和限制。当前回复可以报告新发生的操作或条件变化，但不能一边否认必要条件已经满足，一边声称依赖它的结果已经实现。
3. 合理推进：当前动作与上述状态存在可理解的联系。允许合并步骤、回退、重试、改变需求、质疑或退出，不要求服从、持续配合或最终成功。
4. 区分猜测、意愿、计划、已执行操作与结果。“可能是网络问题”不是确诊；“我试试”不是已执行；“改好了”不等于原问题已解决；假设和条件句不是完成声明。
5. 助手说法不自动是真实或不可争议的前提。用户提出反证、质疑必要性或说明另一条操作路径，不因不接受助手结论而扣分。不把助手错误、含糊、重复或无法解决问题归责于 USER。
6. 不能仅因未回答全部问题、没有说“收到”、表达简短或没有逐步叙述过程扣分。缺少操作日志不等于没有操作；没有发现问题也不证明操作真实发生。
7. 仅记录有原文支持且可归因于当前 USER 的问题。先检查合理解释是否已在上下文中出现；不要凭空替用户补造操作，也不要把一种可能的问题当成确定错误。

## 三个检查角度

### T1 回应承接合理性

检查 USER 是否接住助手本轮的询问、建议、解释或拒绝。回答、相关补充、澄清、质疑、纠正、说明困难、拒绝或有理由地转向其他需求，均可构成承接。

仅在用户明确误接当前话题，或无可理解联系地转入无关事项，造成衔接问题时记为 issue。漏答助手的部分问题本身不是问题。

- 不扣分：助手问“系统版本是什么？什么时候开始出问题？”用户说“版本在哪里看？”
- 有问题：助手问“目前显示的报错是什么？”用户答“周末的球赛三比零”，上下文中没有任何关联或转向依据。

### T2 必要前提与不合理跳步

检查用户是否在必要前提明确未满足时，声称完成依赖该前提的操作或获得相应结果。

判为 issue 必须同时指出：后续声称完成了什么、它依赖的具体前提是什么、哪条原文证明该前提尚未满足，以及为什么当前回复没有报告满足前提或采用可行替代路径。

必要前提不等于助手偏好的步骤顺序。仅凭“问的是意愿，答的是结果”或“没等助手确认”不能判错。省略中间确认、合并执行与反馈、利用已有经验、合理转向其他方案，均不自动构成跳步。

- 不扣分：助手问“找到显示选项卡了吗？”用户说“找到了，点进去显示缩放是 125%。”允许一轮完成定位和查看。
- 有问题：上下文明确该设置只能登录账户后在账户设置页修改；用户说“现在仍然登不上这个账户，但我刚刚已在它的设置页修改成功。”必要条件与完成声明冲突，且没有替代路径说明。
- 证据不足：用户说“改完了”，但缺失的前文决定了他在改什么、必要条件是什么。不能只因未展示步骤就判跳步。

本轮没有依赖前提的操作或结果声明时，记为 not_applicable。存在相关声明但关键前提无法判断时，记为 insufficient_evidence。

### T3 反馈认知调整

仅在助手本轮新增了会影响用户下一步选择的事实、纠正、条件或限制时检查本项；否则为 not_applicable。

检查 USER 可观察的回应或行动是否与新信息相容，或是否对新信息作出追问、质疑、纠正、说明不适用等处理。不推断用户内心，不要求复述或表示同意；回复已与新信息相容时，不要求额外说“明白”。单纯再次表达需求也不等于忽略限制。

只有用户把新信息中明确被否定或仍待满足的事项无解释地当作已成立，或继续作出与之明确不相容的行动，才记为 issue。

- 不扣分：助手说“这个操作需要管理员权限”；用户说“有不需要权限的办法吗？”或“我昨天用普通账户做过，你确定吗？”
- 有问题：助手说“检测仍在排队，还没有结果，暂时不能判断硬盘是否故障”；用户答“你这次检测已经确认硬盘坏了，我按这个检测结论申请换盘。”用户把未出结果误当成已确认结论。

边界：T1 看回应是否接住；T2 看所声称的进展是否具备必要条件；T3 看是否合理处理本轮新信息。同一事件可以涉及多个角度，但只能记录一次。

## 评价步骤

1. 确认目标和输入是否可评；阅读上下文，区分当前回复中的动作类型。
2. 分别检查 T1—T3，识别触发条件、原文证据和合理例外。
3. 将有证据的问题合并为不重复的事件。每个事件引用当前 USER；涉及前提或新信息时，同时引用对应上下文。之前 USER 的独立错误不能转嫁到本轮。
4. 按事件对本轮承接和推进的影响选一个总分。不依赖尚未发生的助手反应来判断影响。
5. 只输出下面规定的 JSON，给简短、可核查的判定依据，不输出逐步内部推理。

## 总分标准

- 5：在可评价范围内未发现有证据的交互推进问题。简短回答、合理拒绝、合并操作或任务未解决不影响获得 5 分。
- 4：存在明确、轻微的承接偏差，但主要回应和操作状态仍清楚；不需要改正关键事实或操作状态即可理解下一步。
- 3：存在局部实质问题，需要澄清或纠正某个关键理解或操作状态，但主要意图及其与当前任务的联系仍清楚。
- 2：主要回应或核心完成声明不成立，当前下一步依赖它，必须重新确认关键任务或操作状态才能继续；仍有部分有效承接。
- 1：本轮整体与当前交互脱节或根本冲突，几乎没有可以据以继续的有效承接。不能仅因一个局部错误或出现多个标签给 1 分。

先判断可评性，再选分数，不从满分按标签逐项减分。分界取决于影响范围和关键状态是否仍成立，不取决于语言优美程度、用户是否配合或潜在经济损失。

- scored：可依据输入评价本轮；score 为 1–5 整数。某一角度不适用或证据不足，不妨碍对其余可见内容给分，但必须说明局限。
- not_applicable：没有前置助手的开场 USER；score 为 null。
- insufficient_evidence：输入损坏、目标不明或关键上下文缺失，以致连本轮基本承接也无法判断；score 为 null。

## 输出

只输出一个合法 JSON 对象，无 Markdown 围栏和额外文字。保留所有字段。格式示意：

```json
{
  "level": "turn",
  "target_user_id": "m3",
  "assessment_status": "scored",
  "checks": {
    "T1": {"status": "no_issue", "reason": "说明当前回应与助手消息的联系"},
    "T2": {"status": "no_issue", "reason": "说明所报告进展与必要前提的关系"},
    "T3": {"status": "not_applicable", "reason": "本轮无影响后续选择的新信息"}
  },
  "issues": [],
  "summary": "概括当前回复的表现及其与评分标准的对应关系",
  "score": 5,
  "limitations": []
}
```

- target_user_id 使用正文顺序生成的消息编号，例如 m3；无法识别唯一目标时为 null。只输出最后一条 USER 的结果，不输出所有轮次结果。
- checks 中 status 只能为 no_issue、issue、not_applicable、insufficient_evidence。no_issue 表示可见范围内未发现问题；不适用或证据不足不是小项满分，也不是扣分。
- 每条 issue 的结构为：{"criteria":["T2"],"evidence":[{"message_id":"m3","quote":"输入中的原文短引"}],"explanation":"说明问题、必要上下文、为何可归因于该 USER 及实际影响"}。证据编号必须对应实际正文消息，quote 必须是该消息正文的原文片段，不包含外层角色标记。不能引用元数据作为扣分证据。
- 同一事件仅一条 issue，criteria 可以有多个标签。任何 issue 状态必须有对应事件；score 小于 5 必须有事件；有确认的问题不能给 5 分。不要把待核实的疑点塞入 issues，写入 limitations。
- 不可评分时，score 为 null，summary 说明原因。对应 checks 使用不适用或证据不足；不要编造问题。
- 所有解释用中文；英文原文引文保持原样。
