# 用户模拟器评测：精简运行版

这个分支只保留运行评测所需的代码、七份 prompt、配置文件、Windows 启动脚本和离线回归测试。需要 Python 3.10 或更高版本，无需安装第三方包。

## 准备数据

在 [运行配置](eval_pipeline/run_config.json)中填写三个输入路径：

- `dialogues`：包含全部模拟对话的 JSON／JSONL 文件，必填。
- `cases`：包含全部案例的 JSON／JSONL 文件，必填。
- `real_dialogues`：包含全部真人对话的 JSON／JSONL 文件，可选；缺失时跳过 B3 真人比较。

可以用仓库外的绝对路径，例如 `D:/评测数据/所有模拟对话.jsonl`。Windows 路径请用 `/`。各文件可以是 JSON 对象数组，或每行一个 JSON 对象。每条对话需要 `case_id`、`session_index` 和 `messages`；每个案例需要 `case_id` 和 `text`。程序也兼容原先的目录输入。

真人对话还支持现有客服导出格式：每条记录以数字作为对话编号，消息列表内用 `用户`、`客服` 标记角色，末尾 `caseID` 数组给出案例编号。程序会从 `caseID` 取案例编号；开头的数字只用作对话编号。该格式的 `caseID` 必须恰有一个非空值。

评测前 10 段时，程序先取这 10 段的 `case_id`，再扫描真人对话大文件，只保留相同案例编号的真人对话供标注和 B3 比较。JSON 数组与逐行 JSON 可以边读边筛选；不会给十几万条真人对话全部调用标注模型。某一批没有同案例真人对话时，该批 B3 不做真人比较；匹配到真人但可比消息不足时，B3 显示证据不足。`manifest.json` 的 `real_reference_selection` 记录扫描和匹配数量。

运行配置默认选择前 10 段模拟对话。将 `limit_dialogues` 改为 `20` 可评前 20 段；设置 `start_dialogue: 11`、`limit_dialogues: 10` 可评第 11–20 段；将 `limit_dialogues` 设为 `null` 可评到文件结尾。这里的序号按文件中的记录顺序计算。`--batch-size` 控制每次 Batch 诊断使用多少段对话，并不限制总评测数量。

## 运行

公司电脑可双击 `run_eval.bat`。在终端中，从仓库根目录运行：

```bash
python3 -m eval_pipeline.runner
```

首次运行前，请核对 [API 配置](eval_pipeline/.local_api.json)中的接口地址和模型名，并确保电脑能访问公司内网服务。也可通过环境变量 `EVAL_BASE_URL`、`EVAL_MODEL`、`EVAL_API_KEY` 覆盖对应配置。只预览任务、不调用模型时，在命令后加 `--dry-run`。

所有模型任务的单次请求默认最多等待 300 秒，超时后默认重试 2 次。临时调整可在运行命令后加 `--timeout 秒数`，例如 `--timeout 600`；不加参数时无需逐项配置。延长等待只对服务处理较慢的情况有帮助，无法解决内网或服务本身不可达的问题。

默认同时执行 3 个模型任务，可用 `--workers 1` 恢复串行，或 `--workers 2` 降低服务压力。例如 `python3 -m eval_pipeline.runner --workers 3`。并发只发生在同一阶段内：先建立案例依据，再做逐轮／整段评测与标签标注，最后做 Batch 比较。评分规则和任务数量不变；服务端支持并行处理时才能明显提速，超时增多时应降低并发。

每阶段会显示任务数，每个新请求会输出耗时并保存 `elapsed_seconds`（包含重试等待）。十段对话通常包含远多于十个请求。按 Ctrl+C 后停止派发新任务，已经发出的最多 `workers` 个任务仍需等待请求及其重试结束并保存，再退出；重跑同一批即可续跑，不要使用 `--force`。并发数不影响缓存匹配。

结果保存在 `results/dialogues_00001-00010/` 等独立目录。每个任务完成后就保存结果；重跑同一组会复用已成功且输入未变的结果，失败和未完成任务会再执行。`summary.json` 是本组摘要，`results.csv` 是逐项结果；不同组的摘要不会自动合并。真人对照标注和分布统计也保存在该组结果目录。

程序实际读取的 prompt 在 `prompts/`；目录中的七个文件均为运行依赖。数据与结果目录已加入 `.gitignore`，不会随普通提交上传。接口配置包含公司提供的访问凭据，此分支应保持私有访问。

## 小指标分数

自然流畅 Turn 输出 T1–T3、Dialogue 输出 D1–D3；单段表达真实性输出 R1–R3；信息泄漏输出 L1–L4。每项的具体分档标准在对应 prompt 中。

- `checks` 保存每项的状态、1–5 分小分、理由和证据（泄漏入口引用事件编号）。分数越高表示确认问题越少或影响越轻。
- `not_applicable` 和 `insufficient_evidence` 的小分为 `null`，在 CSV 中留空，不能解释为满分或零分。
- `results.csv` 新增 `T1_score`、`T1_status`、`T1_reason` 等列，覆盖全部 13 个小项；每行只填写该评测入口对应的列。
- 自然流畅与表达真实性保留独立的整体评分，不平均小分。泄漏总分按去重事件扣分；入口小分仅按该入口的唯一事件扣分，同一事实重复出现不重复扣分。
- B1/B2/B3 仍为诊断状态和统计比较，不生成小分，也不与其他分数相加。

## 信息泄漏的两个阶段

1. 对本次模拟对话涉及的每个案例运行 `case_information_evidence.md`，只读该案例原文，提取事实、原文引用、信息等级、答案属性及获知/披露条件。引用必须能在对应原文位置找到；未知等级与条件保持未知。
2. 保存第一阶段结果后，程序从文件读取成功且可用的依据，连同原案例和模拟对话传给 `information_leakage_dialogue.md`。每个确认泄漏事件必须引用有效的 `fact_ids`，且其中有获知/披露条件。依据失败或完全不足时，对应泄漏任务明确跳过；其他评测继续。

输出位置：

- `results/case_evidence/<服务标识>/results/<任务编号>.json`：完整案例依据结果，包括模型、prompt 摘要、运行状态及 `result.facts`。失败时也即时保存 `error` 和可取得的原始回复。
- `results/dialogues_00001-00010/case_evidence_index.json`：本次使用的案例编号、依据文件路径与任务编号。
- 同组 `results/` 下也保存依据结果副本，便于随本组结果核查；`requests/` 保存实际发送的两阶段 prompt。

同一案例在不同对话及不同切片中复用依据。案例文本、提取 prompt、模型或服务地址改变会生成新的依据缓存；`--force` 强制重新生成。泄漏请求包含依据正文，因此依据改变也会使原泄漏评测缓存失效。`--dry-run` 不调用模型，只列出待生成的案例依据和等待它的泄漏任务，不编造占位依据参与评分。

兼容模型将明确的数字分数写成字符串、将单个表达标签写成字符串等常见格式；已保存且输出完整的失败回复会先尝试重新解析，成功时显示 `recovered`，不再请求模型。含义不明确的值和缺失的必要字段仍会失败。每个失败任务会在终端直接显示简短原因，完整原始回复留在对应任务 JSON 中。

案例依据中的引句若与原文只有空格、换行、全角或标点差异，程序会恢复为原文中的连续片段；位置下标填错且匹配唯一时也会更正。`source_location_corrections` 记录原引句及位置与更正结果。引句找不到或来源不唯一时，只排除对应事实或条件，并把案例依据标为 `partial`；如果没有任何可核实事实，则标为 `insufficient_evidence`，跳过该案例的信息泄漏评分。`excluded_facts` 和 `limitations` 保留具体排除原因。不会将语义相似但无法核实的改写当作原文引用。

提取结果是模型生成的核验材料，不是人工确认事实。代码能检查结构、原文引用和计分一致性，但无法保证模型对知识边界的语义理解正确；正式使用前应抽查 `facts` 的等级和条件，以及事件的来源判断。案例原文没有明确边界时，不能仅凭用户答中答案判定泄漏。

尤其要核查操作指南：其中的步骤顺序不等于用户当时的知识或披露限制。模型有时会把“先点击、再打开”写成必须先执行才能说出方案的条件；仅凭这种提取结果不能确认信息泄漏。

## 更新与检查

本次评分规则变更后，相关旧评测缓存不再直接作为新结果使用；同案例真人标注规则未变，可继续复用符合条件的缓存。离线回归测试无需接口、第三方包或真实数据：

```bash
python3 -m unittest discover -s tests -v
```

公司通过 VS Code SSH 使用 Linux 时，在仓库根目录运行 `python -m eval_pipeline.runner`；Windows 本地可用 `run_eval.bat`。不要将另一台机器的 `run_config.json` 或 `.local_api.json` 覆盖公司当前配置。
