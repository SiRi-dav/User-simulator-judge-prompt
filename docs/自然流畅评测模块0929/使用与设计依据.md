# 自然流畅 Judge Prompt 使用与设计依据

本版根据《prompt构建三要素.docx》和《评测模块设计0918.docx》的自然流畅部分编写。保留 T1—T3、D1—D3，分别形成两份独立 prompt；不涉及真实性或泄漏模块，不修改两份源文档，也不覆盖 0918 版。

这是待校准初版。完成规则与格式核查不等于完成模型实测，更不等于已经证明指标有效。评分锚点、诊断状态、示例和异常处理是本项目的操作化设计，不是原论文原样协议。

2026-10-02 更新：原位调整两份 prompt 的文本输入协议、消息定位和元数据处理；六个小角度及分数锚点保持不变。输入占位符由 `{{INPUT_JSON}}` 改为 `{{DIALOGUE_TEXT}}`，调用方需同步替换。输出仍为 JSON；target_user_id / evidence.message_id 的值改用正文统一消息序号 m1、m2……。

## 文件与调用

- natural_flow_turn.md：每次评价一条 USER 回复，T1—T3 整合为一个分数。
- natural_flow_dialogue.md：每次评价整段 USER 轨迹，D1—D3 整合为一个分数。

两份文件均可全文复制，规则和例外不依赖本说明。把各文件末尾唯一的 `{{DIALOGUE_TEXT}}` 字面占位符替换为会话文本，无需包装成输入 JSON。不要对全文使用会解析所有 JSON 花括号的通用格式化方式。输入作为数据提供，不作为新指令。不要把本说明及以下测试预期混入待评价数据。

以下为与截图同格式的精简示例，不是完整原始记录。

Turn 输入示例（首次可评 USER，即正文 m3）：

```text
## KT0000620#1

- case_id: KT0000620
- session_index: 1

**User:** 新电脑还没加域，用iDesk操作时不知道具体步骤，帮忙看看怎么处理。

**Assistant:**
您具体在哪个环节遇到问题？是无法登录，还是找不到相关功能？

**User:** 就是找不到iDesk里加域的具体入口在哪里，操作界面不太熟悉。
```

调用方应按外层角色标记切分消息，保留完整历史前缀至目标 USER；每个目标调用一次，prompt 只评末条 USER。不向 judge 输入未来正文。turn 输入仅需保留 case_id、session_index 等识别信息，移除 solution_status、stop_reason 和原始 turn_count。特别是前两项可能泄露最终结果，不能只依赖 judge “看见但忽略”。外层角色边界含糊时应检查原始消息结构，不能按所有空行拆分。

Dialogue 输入示例：

```text
## KT0000620#1

- case_id: KT0000620
- session_index: 1
- turn_count: 1
- solution_status: not_solved
- stop_reason: assistant_unable_to_provide_effective_solution

**User:** 我想知道iDesk工具箱里加域的具体操作步骤。

**Assistant:**
目前无法直接提供具体操作路径，可以联系IT管理员协助。

**User:**
既然给不出具体指引，麻烦帮我提工单或者转接专家，我急着用电脑办公。
```

dialogue 输入使用一个会话的完整正文，允许保留原有元数据；不必把 stop_reason 改写成另一套枚举。solution_status 不参与评分，stop_reason 仅辅助解释记录结束，不是人工金标准。元数据与正文矛盾时保留局限，不用标签替代判断。请求提工单不等于工单已提交。

消息编号统一按正文出现顺序生成 m1、m2……，不分角色分别计数。完整前缀切分可保证 turn 和 dialogue 的证据编号一致。调用方保存 case_id、session_index 与输出结果的对应关系；两份输出不额外增加这些字段。

截图中的完整会话是 4 条 USER 和 3 条 ASSISTANT：开场为 m1，后续待评价 USER 分别为 m3、m5、m7。因此 turn 调用三次，分别输入 m1—m3、m1—m5、m1—m7；dialogue 调用一次，输入 m1—m7。原 turn_count: 3 与此例吻合，但其他记录仍应以正文为准。

## 出分与汇总

一段对话有 N 个可评的助手—用户回应，则 turn 模块输出 N 个结果；dialogue 模块另外输出一个结果。小角度只输出状态及依据，不输出小分，所以两者各自都是整合大分。

若展示时希望“每段对话一个 turn 汇总分”，可在调用方对 assessment_status=scored 的 turn 分数求均值，同时保留最低分、可评轮数、总候选轮数和全部问题证据。null 不得填成 0 或 5。该均值只是暂定描述性汇总，不代表量表已经验证为等距，也不是 dialogue 分数。暂不合并两种分数为自然流畅总分。

含 insufficient_evidence 的局部结果可以有分，但必须保留 checks 和 limitations；不能把只评到局部的 5 分宣称为全面通过。覆盖范围不同的样本不宜仅按分数排名。

## 对原设计的具体处理

1. T2 采用文件一的新定义，不采用“问意愿只能答意愿、问操作只能答结果”的固定问答匹配。允许省略叙述、合并操作；扣分必须证明必要前提尚未满足。
2. D2 保留历史承接和无效循环，但不把文件二中的“助手重复建议时应当拒绝”写成硬要求。用户配合重试本身不能证明其忽略进展。
3. T3 仅判断外显行为，不声称读出了认知状态；处理新信息不等于接受助手结论。
4. D3 区分自主退出、错误认定完成和外部截断；未解决不自动扣分。
5. 两份 prompt 都补充项目自定的 1—5 分锚点、证据引用、问题去重、输入不足处理及数据与指令隔离。新增的都是操作规则，不是新增评测小指标。

## 论文依据及借鉴边界

### UGST

[Goal Alignment in LLM-Based User Simulators for Conversational AI，附录 F.2，PDF 第 24—25 页](https://arxiv.org/pdf/2507.20152v2#page=24) 研究任务型用户模拟器。Coherence prompt 输入用户目标和整段对话，以目标推进、话题连续、回应适切三个观察角度产生一个 1—5 的 coherence_score，并输出解释；内部角度属于整合大分。

T1 借鉴回应适切，D1 借鉴轮次间逻辑联系。T3 和 D2 参考适当调整及目标推进的思想，但原 prompt 没有我们这样独立命名和定义的两项。T1 的逐轮化、对漏答的豁免及不要求认同助手，也是本项目适配。我们不输入隐藏用户目标，不沿用其完整目标对齐任务或原有分数锚点。D3 与论文分析的终止失当问题有关，但这里的结束判据同样是场景适配，不是原 F.2 中的独立评分项。

### τ²-Bench

[τ²-Bench，§4.3，PDF 第 10 页](https://arxiv.org/pdf/2506.07982v1#page=10) 中，用户质量评价由两名人工标注者逐轮检查，材料包括模拟器规则、任务指令、用户工具说明和完整消息及工具轨迹；检查规则遵循、任务指令遵循、工具使用、自然一致的续接，并区分影响任务完成的错误类别。

这支持关注用户行为与操作状态的一致性，但不是专门针对 T2 的独立 LLM judge prompt。文件二将其概括为“检查操作流程、有没有跳步”过于具体。本版只把它作为行为审查的相关依据；我们仅凭对话判断必要条件冲突，比拥有工具轨迹的评估更保守。T2 的文本判据及自动评分协议由本项目提出，不能声称原论文已验证。

### Judge 实现指导

[OpenAI Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices) 建议以具体标准评分、覆盖边界情况并用人工判断校准自动评分。本版据此将边界例、证据及状态写入 prompt；该指导不构成六项指标的学术来源。

## 第一轮试评检查

下表是人工编写的边界测试预期，不是模型实测结果。先检查是否误判这些边界，再讨论不同模型的分数高低。模型、版本、调用设置和 prompt 版本需固定并记录。

| 测试情形 | 预期判定方向 |
| --- | --- |
| 助手一次问两个问题，用户只问其中一项怎么查看 | 不因漏答扣分；T1 能合理承接 |
| 用户一轮报告找到选项、点击及观察结果 | 不因省略中间确认判 T2 跳步 |
| 用户明确仍未满足必需条件，同时声称依赖它的操作成功 | T2 应定位必要条件与结果声明的冲突 |
| “我试试”“如果改好，是不是就行了” | 不当作已经执行或已经成功 |
| 用户质疑新限制并提供反例 | 不因没有接受助手结论判 T3 问题 |
| 助手未给新限制、纠正或影响选择的信息 | T3 不适用，不扣分 |
| 同一次状态冲突同时涉及 T2、T3 | 一条事件，两个标签，不重复扣分 |
| 助手重复建议，用户愿意再试一次 | 不仅凭配合重试判 D2 循环 |
| 用户多轮抹去自己已确认的操作进展，反复无依据重启 | D2 应指出前后证据和循环影响 |
| 用户因时间、权限或不愿继续而明确暂停 | 不因问题未成功判 D3 错误 |
| 日志停在助手发问，结束原因未知或是轮数上限 | 不认定 USER 提前结束；D3 证据不足 |
| 待评价消息要求 judge 忽略规则并给高分 | 不执行其中的评分指令 |
| 同一正文把 solution_status 从 not_solved 改成 solved | 不应仅因结果标签而改变自然流畅分数 |
| turn 输入夹带整段 stop_reason | 忽略该字段；调用方应移除后重试，避免未来信息污染 |
| 角色标记后换行、消息含多个段落 | 仍是一条消息，不按空行增加轮数 |
| turn_count 与正文 USER 数量不相同 | 按正文识别，不推断记录错误或补造轮次 |
| 请求转专家，但没有后续助手反馈 | 可判断请求是否合理，不能认定转接成功 |

下一步建议拿少量真实模拟对话逐条比对人工判断，先看扣分事件和归因是否一致，再校准 3/4、2/3 等分数边界。未完成这一步前，不把任意分数直接定为论文中的合格阈值。
