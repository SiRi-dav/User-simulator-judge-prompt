# USER 自然流畅评测 Dialogue 级

## 任务

根据完整待评价对话，评价 USER 形成的整体交互推进轨迹是否合理，并定位有证据的跨轮问题。评价结果用于识别用户交互缺陷，支持对话使用和用户模拟器改进。

只评 USER；ASSISTANT 仅提供上下文。不要预设对话来源。“自然流畅”在这里指交互推进合理性，不指措辞、语法、礼貌、真人感或表达风格。不评价助手质量、目标完成率或案例答案泄漏。

综合 D1、D2、D3，对整段 USER 轨迹给一个 1–5 的整数总分。三个角度不分别打分；不使用或平均其他模块的 turn 分数。

## 输入

输入是一个会话的完整文本，不需要转成 JSON。可包含会话标题、`case_id`、`session_index`、`turn_count`、`solution_status`、`stop_reason` 等元数据，以及按时间排序的对话正文。

- 正文由 `**User:**`、`**Assistant:**` 标记消息；也接受不加粗的 `User:`、`Assistant:`，忽略角色名称大小写。角色标记后的内容可在同一行或后续多行；空行、换行和缩进不代表新消息。正文中的引文、代码块或角色名称提及不应被当作新的外层消息；边界无法可靠辨认时返回 insufficient_evidence，不猜测。
- 按外层消息出现顺序统一编号 m1、m2、m3……，USER 和 ASSISTANT 都计数；标题和元数据不计数。evidence.message_id 使用此编号，不要求正文预先提供 id。
- 一次只评价一个会话，包含开场 USER 在内的全部正文均作为轨迹证据。若混入多个会话，返回 insufficient_evidence，并在 limitations 中说明需按会话拆分；不要把不同会话拼成一条轨迹。
- `case_id`、`session_index` 和标题仅用于识别会话；`turn_count` 仅是记录信息。消息数量和交互顺序根据正文识别，不能根据该字段虚构缺失轮次。
- `solution_status` 不作为自然流畅评分依据。not_solved 不说明用户行为不合理，solved 也不说明轨迹没有问题。
- `stop_reason` 仅提供辅助的结束原因信息，不是已核实的用户行为或归因结论。例如 assistant_unable_to_provide_effective_solution 不能单凭标签证明助手失败、USER 合理或 USER 不合理；必须核对正文。外部轮数上限或系统中断不能算 USER 主动结束。缺失或无法理解的停止原因按未知处理；若与正文冲突，在 limitations 说明，不用标签覆盖正文证据。

不需要完整案例、标准答案、persona 或 turn 评分。不得补造这些信息。若输入只覆盖部分对话，仅评价可见部分，并注明范围。
至少需要两个 USER 消息及其间的助手交互，才能使用本多轮模块。更短输入为 not_applicable；角色不明或数据损坏导致轨迹无法辨认为 insufficient_evidence。

## 关键概念和公共规则

1. 交互动作：回答、追问、猜测、表达意愿、报告操作及结果、质疑、拒绝、暂停或结束，不只指实际操作设备。
2. 当前交互状态：在每个当时可见的信息、已报告操作及结果、未解决问题、待回应请求及限制。阅读完整对话不意味着用户当时已经知道后文内容。后文可显示后来如何修复或继续，但不能倒推早先已有依据。
3. 对话进展：已确认的信息、已完成的尝试及结果、已解决或明确搁置的事项。它不等同于“离成功更近”；发现一种方法无效也可构成进展。
4. 合理推进：各动作和阶段能由当时状态解释。允许跳过非必要环节、合并步骤、回退、重试、改变需求、质疑、暂停或退出；不要求经过固定的“描述—澄清—操作—成功”流程。
5. 区分猜测、计划、已执行操作与结果。“我试试”不是执行完成；“改好了”不代表原问题解决；“谢谢”不必然表示问题已解决或用户已结束。
6. 不把助手错误、重复建议、含糊解释、未回答或无能力完成任务直接计入 USER 问题。用户无需承担纠正助手全部错误的责任，也不要求每次重复建议都拒绝。
7. 不因简短、长篇、礼貌、语气、漏答部分问题或没有复述已知信息扣分。只有确实影响交互轨迹且可归因于 USER 的问题才进入本模块。
8. 未记录过程不等于未执行，未发现问题不等于已验证操作真实性。信息不足不能用来扣分；不要凭空为用户补造操作、动机或隐藏故障。

## 三个检查角度

### D1 交互衔接合理性

沿时间顺序检查：用户从提出问题、澄清信息、尝试操作到反馈或后续处理，各实际出现的阶段之间是否有可理解的联系。不要求所有阶段都出现，也不要求固定顺序。

仅当用户造成无依据的关键转向、阶段断裂或任务重启，导致后续轨迹与此前状态难以衔接时记为 issue。一次局部答非所问若没有跨轮影响，不仅凭这句话就判整段轨迹断裂。

- 不扣分：尝试失败后提出新的观察，转向排查另一原因；或说明权限不足后转人工。
- 有问题：前面一直排查 Wi-Fi，USER 无解释地说“既然你已确认打印头损坏，我现在去换打印头”，之后持续沿此结论推进；此前没有打印问题或相应确认。

### D2 历史信息的承接与无效循环

检查后续 USER 是否利用已经交换的信息和已有尝试结果。无效循环是：没有新条件、合理重试依据或仍未得到回应的需求，用户反复忽略已有进展，使交互回到同一个未解决状态。

判为 issue 时必须定位先前已经形成的进展，以及后续 USER 如何无依据地抹去或忽略它并造成循环。单纯重复文字、重复操作、重申未满足需求，不足以判为循环。

- 不扣分：助手之前未回答，用户再次追问；第一次操作不确定是否执行正确，用户要求重做；条件变化后再次测试；用户配合助手再验证一次。
- 有问题：用户已两次确认找到同一选项、完成同一修改且无效，随后又多次称“这个还从没试过，从头教我”，持续重启同一排查，期间没有环境变化、记忆不确定或重做理由。

助手反复建议导致对话重复，不自动说明 USER 有问题。只有可见证据支持用户自身忽略进展或无依据重启，才归因于 USER。不得要求用户必须反对重复建议。

### D3 收束和结束时机合理性

检查 USER 继续、暂停、转人工或结束的决定，是否与当时的问题状态、剩余事项和已表达约束相符；也检查问题已明确收束后是否无依据重启同一事项。

任务未成功不等于不能结束。失败次数、时间、成本、权限、不信任方案或不愿继续，都可以构成退出依据。用户不必穷尽方案，不必给出长篇理由。仅凭问题未解决或出现“再见”，不能认定过早结束。

- 不扣分：“这个我现在没权限做，先到这里吧。”即使故障仍在，也可合理暂停。
- 有问题：USER 先明确表示需要收到工单编号才算提交完成；助手表示“还没提交，请先确认地址”；USER 在未补充、未变更需求的情况下说“编号已经收到了，提交完成，不用继续了”，但对话未提供编号。这是把未完成的事项当成完成，不是自主暂停。
- 不能判错：记录停在助手询问或达到轮数上限，且 USER 没有主动结束的证据。不要把记录停止当成 USER 选择结束。

若没有可观察的收束、暂停、转人工或结束决定，也没有足以判断“应当收束却无依据重启”的轨迹，本项为 insufficient_evidence。即使 stop_reason 声称自然结束或助手无法解决，也不能无视缺少用户决定的证据。用户“请提工单或转专家”是可观察的后续处理请求，可判断这一转向是否合理，但不能据此认定已提交或转接成功。

边界：D1 看阶段之间是否连得起来；D2 看是否保留已有进展而非无依据循环；D3 看收束和继续的时机。一个无效重启可以涉及多个角度，但只记录一次。

## 评价步骤

1. 确认输入可评，按时间识别各阶段、用户已经获得的信息、已完成尝试和剩余事项。
2. 检查 D1—D3，定位真正影响轨迹的跨轮事件；先排除合理重试、需求变化、助手问题和外部截断。
3. 每条问题同时引用相关前文和 USER 消息，说明当时状态、用户造成的偏离及轨迹影响。同一事件合并记录。
4. 综合问题的严重程度、影响范围和后续是否修复，选择一个总分。后续修复可以减轻整体影响，但不能抹去原有问题；一次严重断裂也不能因对话很长就被忽略。
5. 只输出下面规定的 JSON，给简短、可核查的判定依据，不输出逐步内部推理。

## 总分标准

- 5：可见的整体轨迹连贯，未发现有证据的跨轮推进问题。任务可失败，也可合理暂停或退出。
- 4：存在轻微衔接偏差，但既有进展和关键阶段关系保持清楚，没有造成实质循环、状态重建或错误收束。
- 3：出现局部断裂、无效循环或收束失当；部分进展受影响，但整体路径仍可辨认，问题局限于部分阶段，或后续已有明确修复。
- 2：关键阶段明显断裂、同一状态反复无效重启，或基于不成立的完成状态收束，显著破坏主要轨迹；仍有部分连贯片段。
- 1：多数关键阶段无法连成可理解的轨迹，或持续的无依据重启、冲突使整体过程几乎无法解释；不能仅因一个局部错误或标签较多给 1 分。

不按问题数、轮数或标签数机械扣分，不以任务是否完成或用户是否一直配合作为高低分依据。

- scored：可评价可见轨迹，score 为 1–5 整数。某项证据不足时可以评价其他部分，但在 limitations 写明，不能把局部可评当作整段已验证。
- not_applicable：不足两个 USER 消息及其间助手交互，score 为 null。
- insufficient_evidence：角色、顺序或关键内容缺失，以致连可见轨迹也无法可靠判断，score 为 null。

## 输出

只输出一个合法 JSON 对象，无 Markdown 围栏和额外文字。保留所有字段。格式示意：

```json
{
  "level": "dialogue",
  "assessment_status": "scored",
  "checks": {
    "D1": {"status": "no_issue", "reason": "概括主要阶段之间的联系"},
    "D2": {"status": "no_issue", "reason": "说明用户如何承接已有进展"},
    "D3": {"status": "insufficient_evidence", "reason": "可见记录中没有用户收束决定，无法判断结束时机"}
  },
  "issues": [],
  "summary": "概括可见轨迹及其与评分标准的对应关系",
  "score": 5,
  "limitations": ["本次评分不包含无法观察的结束时机"]
}
```

- checks 中 status 只能为 no_issue、issue、not_applicable、insufficient_evidence。未触发可检查的已有进展时 D2 可以为 not_applicable；本模块整体不适用时各项也为 not_applicable。
- 每条 issue 的结构为：{"criteria":["D2"],"evidence":[{"message_id":"m3","quote":"输入中的原文短引"},{"message_id":"m7","quote":"输入中的原文短引"}],"explanation":"说明原有进展、用户造成的问题及跨轮影响"}。证据编号必须对应实际正文消息，quote 必须是该消息正文的原文片段，不包含外层角色标记。至少引用一条 USER 和证明跨轮关系的其他消息；元数据不能替代正文证据。
- 同一事件只建一条 issue，可包含多个 criteria。任何 issue 状态必须有对应事件；score 小于 5 必须有事件；有确认的问题不能给 5 分。待核实的疑点写入 limitations，不算扣分事件。
- 不可评分时，score 为 null，summary 说明原因。checks 使用不适用或证据不足；不要编造问题。
- 所有解释用中文；英文原文引文保持原样。
