# 用户表达真实性评测 单段对话

## 任务

阅读待评价对话，结合交流情境，评价 USER 的表达方式是否可信，并指出有具体证据支持的表达问题。结果用于定位表达问题，并支持后续质量比较和修改。

只评价 USER。ASSISTANT 的发言仅用于理解用户为什么采用某种说法、篇幅或结构，不评价助手质量。不要预设对话来源，也不要判断它实际由真人还是 AI 生成。

围绕 R1、R2、R3 三个角度，对整段 USER 表达给一个 1–5 的整数总分，不分别给小分。不评价事实正确性、知识泄漏、任务完成、合作程度、操作是否正确或交互推进是否合理。

## 输入

输入是一段原始 Markdown 对话，不要求转换为消息 JSON，也不要求预先给消息编号。典型结构为：

```markdown
## KT00000620#1

- case_id: KT00000620
- session_index: 1
- turn_count: 3
- solution_status: not_solved
- stop_reason: assistant_unable_to_provide_effective_solution

**User:** 用户原文

**Assistant:**
助手原文，可以包含多个段落。

**User:** 用户的下一条回复
```

按以下规则读取：

1. 将对话标题中的编号（如 KT00000620#1）作为输出 dialogue_id。没有标题时，只有 case_id 和 session_index 都存在才用“case_id#session_index”组合编号；均无法取得时输出 null 并说明，不编造案例编号。标题与元数据不一致时保留标题编号，在 limitations 记录冲突。
2. 以导出记录的消息起始标记 `**User:**`、`**Assistant:**` 识别角色，大小写不影响识别。正文可与标记同一行，也可从下一行开始；直到下一条真实消息标记前的段落均属于本条消息。空行、缩进、列表或换行本身不新增消息。
3. 在本段对话内按出现顺序将用户消息编号为 U1、U2……，助手消息编号为 A1、A2……，用于输出 evidence.message_id。两类分别计数；不修改原文，不要求输入已有编号。引用或代码块内部的角色标签不是新消息；如果边界确实无法辨认，说明不确定性，不猜测角色。
4. case_id、session_index 只用于记录定位。turn_count 仅为导出元数据，不用于推算或截取消息数量，按正文读取全部消息。例如 turn_count 为 3 时，正文仍可能有 U1–U4 和 A1–A3。
5. solution_status、stop_reason 及其他结果、来源标签不作为真实性评分证据。不因 not_solved、助手失败、轮数上限或转人工扣分，也不能据这些标签补造用户意图。需要理解语气或重复原因时，依据实际对话正文。
6. 输入若附明确用户背景，只用于理解表达，不作为必须逐项符合的画像评分表。无需完整案例、标准答案、模拟器内部状态或其他模块评分；不得补造。

本 prompt 每次只评一段对话。若输入包含多个独立会话，不将它们合并评分；返回 insufficient_evidence、overall_score=null，并说明需要按会话拆分或使用批量模块。

## 判定边界

“表达真实性”指当前情境下真实用户可能采用的表达方式，不指书面语言是否完美。交流情境包括助手的表达要求、当前谈论内容、此前说过什么和明确提供的用户背景。不得自行假设用户年龄、职业、性格、母语或表达习惯。

- 正式、专业、礼貌、长回复、分条、完整句，均不自动扣分。
- 简短、口语、省略、错字、情绪词，均不自动加分；不要求用户刻意表现这些特征。
- 用户可以提供知识、提出方案、纠正助手、拒绝或保持耐心。不要把这些行为本身当作表达问题。
- 用户不必回答助手的全部问题；主动多说一些信息也不自动构成问题。本模块只检查这些内容的表达是否出现有证据的不适切。
- 不以“我不这样说”“一般真人不会这样”作为充分理由。每条负面判断都要指出具体表达特征及上下文为何不能合理解释它。
- 不把复制的报错、引用的客服原话、日志或助手要求使用的格式，直接视为用户自己的措辞习惯。先区分引用内容与用户自行组织的表达。

## 三个观察角度

### R1 措辞与语气的自然性

检查具体词句和语气是否与当前交流用途相称。重点找：难以解释的生硬搭配、不合场景的宣传或服务套话、堆叠情绪词而缺乏具体表达内容的表演式口语。

判为问题时，必须指出哪段词句存在什么异常，以及为什么不是可理解的个人表达差异。单个错字、省略、语法不规范、方言或少见说法不构成扣分依据；情绪强烈也不自动说明不真实。

- 不扣分：故障反复发生后，用户说“又断了，真的烦”；用户平静地说“客户端连接依然失败，请协助确认”。两者都可以可信。
- 问题候选：助手只问版本号，用户自行写“尊享卓越排障体验，共创高效服务新篇章，我的版本是 16.0”。如果没有引用、玩笑等语境依据，可指出宣传套话与当前用途不相称；不是因为礼貌或正式而扣分。

### R2 信息表达的组织与详略适切性

检查一条 USER 消息如何展开：篇幅、分条、说明、复述和总结是否服务于当前表达需要。

重点找：简单确认也作长篇铺陈；反复重写双方已知背景；使用背景、分析、结论等完整报告结构，却没有需要这样说明的内容。必须定位多余的展开方式，不能只因回复长或信息多而扣分。

- 不扣分：助手要求“按发生时间、报错、已尝试操作三点说明”，用户逐项详细回答；用户为避免误解而总结已试过的方法。
- 问题候选：助手只问“找到选项了吗”，用户确认后又重写此前的完整故障背景、排查目的和抽象总结，既未补充情况，也不是在澄清或按要求报告。可检查这些铺陈是否不合当轮需要。

### R3 跨轮表达的非机械化

把多个 USER 回合放在一起，检查其是否在不同表达需要下反复套用同一套措辞或组织框架。

“机械模式”是相似表达在多个回合复现，且不能由相似任务、必要确认、引用或固定格式要求合理解释。相同结构不要求逐字相同，例如每轮均为“感谢解释—完整复述—总结理解—提出下一问”。

- 不扣分：多次回答“好的”；保持相同正式程度；沿用术语；再次强调尚未得到回应的问题；助手连续要求按同一格式报告结果。
- 问题候选：助手分别询问版本、解释设置含义、确认操作结果，用户每次都先写长篇感谢、再复述助手全部内容、最后总结并追问，且这些重复部分没有对应的交流需要。
- 判为问题必须引用至少两个不同 USER 回合，说明共同模式及为何缺少情境依据。两个例子只是最低引用要求，不代表复现两次就必然有问题；证据只能支持局部重复时，不夸大为“每轮如此”。
- 只有一条可读 USER 消息时，R3 证据不足，不因而扣分。多条消息但只有重复的简单确认，也不能据此强判机械化。

R1 看词句和语气，R2 看单条消息的组织与展开，R3 看跨轮复用。同一段长篇套话可以涉及多个角度，但只记录一个问题模式，不重复扣分。重复任务或反复操作不属于 R3，除非其表达本身也符合上述机械模式。

## 评价步骤

1. 阅读整段对话，确认角色、顺序和可评价范围；结合当时上下文理解每条 USER 的表达需要。
2. 检查 R1–R3。发现可疑表达后，先排除引用、格式要求、合理说明、稳定个人风格等解释。后文可以帮助辨认重复模式，不能要求用户提前知道后文信息。
3. 只保留有具体证据的问题，合并重复证据和同一问题模式。无法确认的疑点写入 limitations，不用于扣分。
4. 根据问题的明显程度、持续程度及覆盖范围选一个整体分数。不要按角度数、问题条数或消息长度机械扣分。
5. 输出指定 JSON，只提供简短判据和可核查证据，不输出逐步内部推理。

## 整体评分标准

- 5：可见表达符合交流需要，未发现有充分证据的不适切或机械模式。允许错字、省略、专业表达、风格稳定，也允许任务失败。
- 4：存在孤立、轻微的措辞或组织不适切；大部分表达仍与情境相称，没有形成主导性的机械模式。
- 3：部分回复出现明显不适切，或局部反复套用表达框架；仍有较多能随交流需要变化的可信表达。
- 2：明显的不适切或无依据套用贯穿多个主要回合，主导了对话中的用户表达；仍能辨认少量情境适切的表达。
- 1：几乎所有可评表达都被严重生硬、表演式或机械套话主导，缺少与实际交流需要相称的表达。不能仅凭一个异常词、一次长回复或没有错字给此分。

按当前可观察范围评分。5 分表示“在可评范围内未发现问题”，不是已证明真人来源。仅一部分角度可评时，保留分数并在 limitations 写明，不能把局部结果说成三个角度均已充分验证。

如果没有可读 USER 内容，或输入的角色、顺序、正文缺失使所有角度都无法可靠评价，assessment_status 为 insufficient_evidence，overall_score 为 null。输入没有消息编号不是缺陷，应按 U1/A1 规则生成引用编号；若消息边界无法可靠辨认，以致证据不能定位，则返回不可评。仅消息很短、仅一条 USER、缺少用户画像或对话标题，均不自动导致整体不可评；缺少标题且无法从元数据取得编号时，dialogue_id 为 null 并在 limitations 说明。

## 输出

只输出一个合法 JSON 对象，不加 Markdown 围栏或其他文字，固定保留以下字段：

```json
{
  "dialogue_id": "原输入编号",
  "assessment_status": "scored",
  "overall_score": 5,
  "summary": "简短说明可见表达特征以及整体判断",
  "findings": [],
  "limitations": []
}
```

- assessment_status 只取 scored 或 insufficient_evidence；前者 overall_score 为 1–5 整数，后者为 null。dialogue_id 按输入读取规则取得；无法取得时返回 null 并说明。
- findings 只记录确认的表达问题。每项结构为：{"criteria":["R2","R3"],"evidence":[{"message_id":"U2","quote":"对应消息中的原文短引"},{"message_id":"U3","quote":"对应消息中的原文短引"}],"explanation":"说明具体表达问题、相关情境及不采用合理例外的依据"}。
- criteria 只能使用 R1、R2、R3。message_id 使用按正文顺序生成的 U1、U2 或 A1、A2 等字符串；quote 必须是该消息正文中的原文片段，不含外层角色标记，不得改写或拼接。每项至少引用一条 USER；必要时另引 ASSISTANT 作为上下文。R3 至少引用两个不同 USER 回合。
- 同一模式只建一条 finding，可以有多个 criteria。不要为满足格式硬找问题。overall_score 小于 5 必须有对应 finding；有确认的扣分问题不能给 5 分。不可评时 findings 为空，不将数据损坏计为用户缺陷。
- limitations 使用简短字符串列表，写明未能评价的角度、记录截断或其他证据限制；没有则为空。原文短引保持原语言，其余说明用中文。
