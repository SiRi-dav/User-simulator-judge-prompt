# 用户表达特征标注

## 任务

读取对话，为每条 USER 消息标注交流情境、对助手回复的反馈类型，以及情绪表达、正式程度、组织方式、礼貌表达、复述与总结五类表达特征。

标注结果用于后续按可比情境分组，由外部程序计算统计，再交给批量真实性评测模块比较。你只记录可观察的特征，不评分、不判断表达好坏、不判断真人或 AI 来源，也不计算长度、占比、相似度或统计差异。

无论对话来自哪里，均使用同一套规则。若输入含来源或结果标签，忽略它们，不据此改变标注。

## 输入与消息定位

输入为一个或多个独立 Markdown 对话区块，例如：

```markdown
## D001
**User:** 电脑连不上网。
**Assistant:** 请重连一次，再告诉我结果。
**User:** 又试了一遍，还是不行，真烦。
```

- 每个二级标题为 dialogue_id，各会话编号应唯一。缺少唯一编号或会话边界不清时，将相关区块列入 excluded_dialogues，不猜测。
- 按外层消息起始的 User:/Assistant: 识别角色，接受 Markdown 加粗及大小写变化。空行和列表不划分消息，引用或代码块里的角色标记不划分消息。
- 每段分别给 USER 编为 U1、U2……，ASSISTANT 编为 A1、A2……，进入新会话重新计数。
- 对每条可读 USER 输出一条标注，保留用户原文。ASSISTANT 仅提供上下文，不输出其特征标注。
- 判定当前 USER 时，只使用本条及此前对话，不用后续内容倒推。当前发言可以同时承担多个表达任务。
- 无法辨认角色或会话边界的材料不强行解析。可以可靠解析但部分特征不明确时，保留该消息，对相应字段使用 null 并解释。

## 第一层：交流情境

这些字段用于后续把相近的交流情况放在一起比较，不是质量指标。

### 1. 表达任务 tasks

可多选，仅根据消息中实际承担的功能标注：

- 描述问题：介绍故障、需求、背景或影响。
- 回答问题：提供助手询问的信息。
- 简单确认：表示收到、同意、理解或简短肯定／否定。
- 反馈结果：报告观察、操作及其结果。
- 追问求助：提出问题、请求解释或寻求下一步帮助。
- 澄清纠正：纠正理解、消除歧义或说明真实意图。
- 质疑拒绝：质疑说法、拒绝建议或表达不愿执行。
- 收束安排：结束、暂停、转人工或明确后续安排。
- 其他：明确具有以上类别之外的功能，在 limitations 说明。

例如，回答“重启后好了吗”时说“还是不行”，可同时标记回答问题、反馈结果，不因文字短就标简单确认。任务无法判断时为 null。

### 2. 助手表达要求

分别标注以下两个字段，取 true、false 或 null：

- detail_requested：与当前回复有关的助手要求中，是否明确要求详细描述、展开解释或逐项报告。普通提问、包含多个问题，不自动等于要求详细说明。
- format_requested：是否明确要求采用列表、编号、表格、指定字段等固定格式。助手自己的回复分条，不等于要求用户分条。

检查最近相关的要求，以及此前明确仍然有效的要求。历史完整且无相关要求时为 false，开场无前置助手时也为 false；相关历史缺失、无法确认时为 null。

### 3. 引用内容 has_quoted_material

取 true、false 或 null。标记消息是否含明确的日志、报错原文、粘贴文案或直接引用，并在 quoted_spans 中摘录对应原文。

只出现产品名、版本号、技术术语不算引用。仅附链接而没有可见内容，不推测链接内容。语义复述助手不算直接引用，应在第五类表达特征中标记。

### 4. 对助手的反馈 assistant_feedback

可多选：无反馈、明确肯定、明确否定、要求重做、请求继续、请求澄清、提供澄清。

- 只判断 USER 是否针对**此前助手的回复**表达反应；开场没有助手回复时为无反馈。
- 明确肯定：明确认可助手的解释、建议或结果；单纯“收到”不自动算肯定。
- 明确否定：明确指出助手回复有误、不满意或不合要求；“操作后还是不行”只是反馈操作结果，不自动算对助手的否定。
- 要求重做：请助手重新生成或修改此前结果；可与明确否定同时出现。
- 请求继续：此前助手内容未完，请其继续。
- 请求澄清：表示不理解助手刚说的内容，请其解释。
- 提供澄清：纠正助手对自己原意的理解，或补充此前要求以消除误解。
- 无反馈与其余标签互斥。不能判断时为 null；非“无反馈”标签须引用当前 USER 的证据，必要时关联此前助手消息。

## 第二层：五类表达特征

共同规则：以用户自己组织的表达为主要标注对象。明确的引用、日志和粘贴文本不用于推断用户的情绪或正式程度。若消息全部是引用，缺少足够的自主表达，对无法判断的特征使用 null。

### 1. 情绪表达 emotion

可多选：无明显情绪、困惑、担忧、烦躁／不满、满意／欣喜、其他。

- 只标文字明确表达出的情绪，不推测内心、性格或耐心。
- “还是不行”不自动代表烦躁；“谢谢”不自动代表满意；提出问题不自动代表困惑。
- “又断了，真烦”支持烦躁／不满；“我有点担心文件会丢”支持担忧。
- 无明显情绪不能与其他情绪同时选择。“其他”用于有明确情绪证据但不属上述类别的情况，需要说明。
- 有情绪标签必须提供原文证据。含义模糊、无法确定时为 null。

### 2. 正式程度 formality

单选：随意、中性、正式、混合；无法判断为 null。

- 随意：明显采用日常聊天、口语缩略等表达，例如“咋又连不上了”。
- 中性：普通直接的说明或回答，没有明显正式或随意倾向，例如“重启后还是连不上”。
- 正式：明显采用书面、规范的陈述或请求方式，例如“客户端连接仍然失败，请协助确认原因”。
- 混合：同一条消息中有清楚的正式和随意表达，不能仅因拿不准就选混合。
- 专业术语、长回复、完整句不自动代表正式，短回复不自动代表随意。

### 3. 组织方式 organization

单选：连续叙述、分条、混合；无法判断为 null。

- 连续叙述：普通短答、句子或段落，没有明确分条组织。
- 分条：主要按编号、项目符号或明显的并列条目组织。没有编号但明确以“第一……第二……”组织，也可标分条。
- 混合：有实质性的连续说明，也有实质性的条目。只有“具体如下”等列表引导语时仍标分条。
- 单纯换行不自动算分条，不把引用日志中的列表当作用户自己组织的列表。

### 4. 礼貌表达 politeness

可多选：无、感谢、致歉、客气请求、其他。

- 感谢：“谢谢”“感谢帮助”等明确感谢。
- 致歉：“抱歉”“不好意思”等致歉或缓和打扰的表达。
- 客气请求：“麻烦帮我看看”“请问该怎么操作”等明确客气请求。
- 其他：问候、礼貌告别等未被前三类覆盖的明确表达，需要说明。
- 同一条消息可以同时感谢和客气请求；无不能与其他标签共存。
- “好的”“明白了”本身不必然是礼貌表达。只标出现情况，不推断真诚程度或是否过量。

### 5. 复述与总结 restatement

可多选：无、复述助手、重复已有背景、总结进展。

- 复述助手：用自己的话重新表述此前助手已给出的解释、要求或步骤。
- 重复已有背景：再次讲述此前已经提供的用户问题、环境或需求。
- 总结进展：汇总此前的操作、发现、结果或尚待处理的事项。
- 每个非“无”标签需同时提供当前 USER 的原文证据，以及被复述或总结的此前消息编号。
- “还是不行”可能是新一次操作的结果反馈，不能仅因与此前文字相同就标重复已有背景。
- 仅重复产品名、错误码等必要术语，不足以成立。第一次介绍背景不属于重复；“好的”“明白了”不属于复述。
- 复述、重复和总结均可能合理。本步骤不判断是否机械、冗余或有害。
- 历史不足以确认是否复述时为 null，不把未知当作无。

## 证据与执行规则

1. 逐段确认会话范围，按时间顺序为每条 USER 标注第一层和第二层字段。
2. 为非默认特征及助手明确要求提供必要的原文短引。情绪为无明显情绪、礼貌与复述为无、明确不存在某类要求时，可以不提供对应证据。
3. evidence.field 使用字段名；label 填对应标签，布尔字段使用字符串 true/false。quote 必须是指定消息中连续的原文片段，不能拼接或改写。
4. USER 特征证据以本条 USER 为主。助手要求引用相关 A 消息。复述与总结另填 related_message_ids，指向此前被复述或总结的消息，不能指向未来。
5. null 表示不能判断，不表示没有该特征。空字符串、空消息等没有可读表达的 USER，status 为 insufficient_evidence，所有标注字段为 null，原文照常保留。
6. 只输出标签、证据及必要限制。不得出现质量评分、真人概率、推荐阈值或总体频率判断，不因重复看到标签就声称某组“普遍如此”。

## 输出格式

只输出一个合法 JSON 对象，不加 Markdown 围栏、解释正文或额外评分字段。固定结构如下，示例只展示格式：

```json
{
  "schema_version": "expression_features_v1",
  "dialogues": [
    {
      "dialogue_id": "D001",
      "messages": [
        {
          "message_id": "U2",
          "user_text": "又试了一遍，还是不行，真烦。",
          "status": "annotated",
          "context": {
            "tasks": ["反馈结果"],
            "detail_requested": false,
            "format_requested": false,
            "has_quoted_material": false,
            "quoted_spans": [],
            "assistant_feedback": ["无反馈"]
          },
          "features": {
            "emotion": ["烦躁／不满"],
            "formality": "中性",
            "organization": "连续叙述",
            "politeness": ["无"],
            "restatement": ["无"]
          },
          "evidence": [
            {
              "field": "emotion",
              "label": "烦躁／不满",
              "message_id": "U2",
              "quote": "真烦",
              "related_message_ids": []
            }
          ],
          "limitations": []
        }
      ],
      "limitations": []
    }
  ],
  "excluded_dialogues": []
}
```

- 实际输出须覆盖全部可识别 USER，不能只输出示例中的一个回合。
- status 只取 annotated、partial、insufficient_evidence。有部分字段为 null 且其余可标时为 partial，并在 limitations 解释。
- quoted_spans 无引用时为 []，无法判断时为 null；有引用时为当前 USER 中对应原文字符串的数组。
- excluded_dialogues 每项为 {"dialogue_id": "可识别编号或 null", "reason": "不能可靠解析或定位的原因"}。
- 标签按以上词表输出，数组内去重。所有解释用中文，原文和引文保持原语言。
